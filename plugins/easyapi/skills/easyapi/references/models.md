# 模型选型与比价

## 三种计费方式

`quota_type` 决定怎么算钱：

| 值 | 名称 | 公式 |
|---|---|---|
| `0` | 按量 | `Σ(各类 token × 对应倍率) × 分组倍率 × 折扣` |
| `1` | 按次 | `model_price × 分组倍率 × 折扣`（图片再乘 `n` 张数） |
| `2` | 按秒 | `秒数 × model_ratio × 该分辨率的按秒倍率 × 分组倍率 × 折扣` |

**是否按秒看有没有配 `video_per_second_ratio(s)`，不看请求里的 `seconds` 参数。**

## 单位换算

- `QuotaPerUnit = 500000`，即 **1 USD = 500,000 quota**
- **1 倍率 = $0.002/1K token = $2/百万 token**
- 系统内部汇率 `USD2RMB = 7.3`

## 用 compare 选型

```bash
# 图片模型对比（按次计费，直接可比）
"$EASYAPI_SKILL_DIR/bin/easyapi" compare --category image

# 视频模型对比，指定时长与分辨率
"$EASYAPI_SKILL_DIR/bin/easyapi" compare --category video --seconds 10 --resolution 1080p

# 指定几个模型对比
"$EASYAPI_SKILL_DIR/bin/easyapi" compare Kling-3.0 seedance-2.0 hailuo-2.3 --seconds 5
```

输出把有价的按价格升序排列，无法本地估算的按原因分组。

## 已知的比价陷阱

这些是核对价格时真实踩过的坑，做选型建议时要留意：

1. **`/pricing` 返回的是「多渠道最低价聚合」，不是全局配置值。**
   后端会把各渠道的覆盖价折算成最低价内联回写。所以接口上的价格可能低于你预期的配置价。

2. **`model_discount` 是否计入实际账单口径不稳定。**
   曾对照实际扣费发现 `/pricing` 里的 `model_discount` 并未生效。因此 `compare` 的
   **预估单价不含折扣**，只把折扣单独列出来作参考。**预估价格只用于横向比较，
   真实金额以平台实际扣费为准**（看轮询结果里的 `billed_cost`）。

3. **`video_input_ratio` 是折扣（< 1），不是加价项。**
   只在「输入含视频」时生效，没有视频输入时不该乘。而且个别模型配的是 > 1 的值（如 Kling 的
   `video_input_per_second_ratio = 1.5`），语义是加价 —— 不要假设它一定小于 1。

4. **按次计费的图片模型要乘 `n`（张数）。** `n` 对按量模型不生效。

5. **`video_ratio` 的形态在三处不同**：全局配置是嵌套 map、渠道条目叫 `video_ratios`、
   `/pricing` 里单值和 map 并存。读接口时以 `/pricing` 的字段名为准。

6. **`create_cache_ratio` ≠ `cache_creation_ratio`。** 后者只是日志里的展示键名，
   配置和渠道覆盖都用前者。写错了会被静默丢弃。

7. **`0` 是合法值**（折扣 0 = 免费，ratio 0 = 免费）。展示时要区分「未配置（—）」和「0（免费）」。

8. **伙伴用户不叠加全局/渠道折扣**，只取伙伴折扣。非伙伴用户 = 全局/渠道折扣 × 平台官方折扣。

9. **工具调用有附加费**（web_search、file_search、image_generation 等），
   不参与折扣、也不被倍率放大，在最后单独相加。

## 给用户做选型建议时

- 先说清楚**计费方式**，再说价格。用户往往不知道视频是按秒算的。
- 视频给价格时要带上假设（「5 秒 720p 约 $0.22」），别只报单价。
- 按量计费的模型（大部分文本模型、部分视频模型）**无法在本地估算**，
  只能给倍率做横向参考 —— 直接说明这一点，不要编一个数字。
- 用户对价格敏感时，建议先跑一个小参数（短视频、低分辨率、`n=1`）验证效果再放大。

## 参数定义从哪来（影响校验效果）

脚本按四级来源取参数定义，并**逐字段合并**：

1. `GET /pricing/schema?all=1`（匿名）—— 一次拉全量，新模型上线自动生效；
   本地缓存 24 小时，`--refresh` 强刷，`pricing_version` 变化时自动作废。
2. `GET /pricing/schema?model_name=<模型>` —— 只有单模型接口的部署。
3. `GET /pricing/detail` 的 `params` —— 更老的部署。
4. 内置快照 `references/model-snapshot.json` —— 完全离线兜底，
   由 `tools/build_snapshot.py --from-api` 从线上重新生成。

高优先级覆盖同名参数，低优先级补齐线上还没声明的参数。所以：

- 管理端（或线上接口）补齐某个模型的 `params`，skill 不用发版就会自动变严格；
- 线上只填了一部分参数时，快照里更完整的枚举/范围仍然生效（不会再整份丢弃）；
- 两者都没有 → **跳过参数校验并明确告知**，请求照发。这是诚实降级，不是静默通过。

⚠️ 后端只转发 `params` 里**声明过**的动态字段（图片的 `Extra`、视频的 `Extra`）。
所以「快照补全」的字段只保证取值形状对，未声明的动态字段仍可能被网关丢弃；
报错时以 schema 里线上声明的字段为准。

**想让传参校验覆盖更多模型，最有效的做法是在管理端补齐这些模型的 `params`。**
